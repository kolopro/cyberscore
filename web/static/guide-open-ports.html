Open ports & attack surface reduction

What open ports reveal about your server, which services belong on the public internet and which don't, and how to close the gaps attackers use most.

In short: Every open port is a potential entry point. Attackers scan the entire internet for open ports in minutes, probing each one for known vulnerabilities. The goal is to expose only what you absolutely must — and ensure everything that is exposed is patched, properly configured, and monitored.

What is a port and why does it matter?

A port is a numbered endpoint on a server — a virtual "door" through which a specific service communicates. Port 80 is HTTP, port 443 is HTTPS, port 22 is SSH. When a service is running and accepting connections on a port, that port is said to be open. When no service is listening or a firewall blocks access, it is closed or filtered.

Your attack surface is the total set of points where an attacker can try to interact with your system. Every open port is part of that surface. A well-configured server running only a web server and nothing else is dramatically safer than one with dozens of open ports from forgotten services or development tools left running.

How attackers use open ports

Automated scanners — tools like Shodan and Masscan — continuously map every IP address on the internet. Within minutes of a server going online, bots are already probing its ports. For each open port they find, they:

  • Identify the service and its version from its banner response
  • Check whether that version has known CVEs (published vulnerabilities)
  • Try default credentials on login services (SSH, RDP, database ports)
  • Probe for misconfigurations — anonymous FTP, unauthenticated Redis, open MongoDB

This is not targeted hacking — it is opportunistic automation that never sleeps. A misconfigured open port discovered at 3 AM is probed within minutes.

Principle of least exposure

The guiding principle of attack surface reduction is simple: expose only what you must, to only those who need it, and nothing more. In practice this means:

  • Close every port that isn't needed. If you do not have an FTP requirement, disable the FTP service entirely — not just block it at the firewall.
  • Bind internal services to localhost. Database servers, caches and admin panels should listen only on 127.0.0.1, not on 0.0.0.0.
  • Restrict management ports by IP. SSH, RDP and admin panels should only be reachable from your known IP address ranges, via firewall rules.
  • Use a VPN for internal tools. Instead of exposing a monitoring dashboard on port 3000, put it behind a VPN. Attackers cannot attack what they cannot reach.

Firewall basics

A firewall is your first line of defence — it drops traffic to closed ports before any service sees it. On Linux servers, ufw (Uncomplicated Firewall) makes this straightforward:

# Allow only HTTP, HTTPS and SSH from anywhere
ufw default deny incoming
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow from YOUR_IP to any port 22
ufw enable
Cloud providers (AWS, GCP, Hetzner, DigitalOcean) also offer security groups or firewall rules at the network level — these are independent of the OS firewall and provide an additional layer. Use both.

How to audit your own open ports

You can check what ports your server is listening on from within the server itself:

# See all listening ports (Linux)
ss -tlnp

# Or with netstat
netstat -tlnp

To see what an attacker sees from outside, you need an external scan. CyberScore's DNS zone tab shows the subdomains your domain resolves to; for a full port audit, tools like Nmap are the standard — but always scan only servers you own or have explicit permission to test.

Server banner suppression

Even when a port must be open, you can reduce what it reveals. By default, many services announce their exact software version in their banner response — giving attackers an easy lookup for known CVEs. Suppress this where possible:

# Nginx — suppress version
server_tokens off;

# Apache — suppress version
ServerTokens Prod
ServerSignature Off

Keeping the surface small over time

Attack surfaces grow as systems do — a new service gets deployed, a developer opens a port for testing and forgets to close it, an upgrade installs a new daemon. Build auditing into your routine: run a port scan after every deployment, review firewall rules quarterly and remove services that are no longer needed.
