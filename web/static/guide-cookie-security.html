Cookie security flags: HttpOnly, Secure and SameSite explained

Three attributes on a cookie header can be the difference between a safe session and a hijacked one. Here's what each does and how to add it.

In short: Every session cookie should carry three flags: Secure (only sent over HTTPS), HttpOnly (not readable by JavaScript, blocks XSS-based theft) and SameSite=Strict or Lax (stops cross-site request forgery). Without them, one XSS or network interception vulnerability becomes a full account takeover.

What is a cookie, in security terms?

When you log into a website, the server typically stores a unique token in a cookie — a small piece of data that your browser sends back automatically on every subsequent request. This is how the server knows you are still logged in. If an attacker can steal or forge that cookie, they can impersonate you without ever knowing your password.

The three security flags on a cookie directly limit the ways an attacker can steal or misuse it.

The Secure flag

When a cookie has the Secure flag, browsers will only send it over an encrypted HTTPS connection — never over plain HTTP. Without it, your session cookie travels in cleartext over any HTTP request, where anyone on the same network (a coffee-shop Wi-Fi, a corporate proxy, a compromised router) can read it.

The Secure flag is only effective when your site enforces HTTPS. Combine it with HSTS to ensure browsers never connect over HTTP in the first place.

The HttpOnly flag

An HttpOnly cookie cannot be read or modified by JavaScript — only by the browser itself when making HTTP requests. This directly limits the damage from a Cross-Site Scripting (XSS) attack.

Without HttpOnly, an XSS payload like document.cookie returns all cookies, and an attacker who injected a script can steal your session token and send it to their server. With HttpOnly set, that JavaScript call returns an empty string — the cookie is invisible to scripts.

HttpOnly does not prevent XSS — it limits its impact. You should still implement Content-Security-Policy to reduce the XSS attack surface.

The SameSite flag

SameSite controls whether the browser sends a cookie along with cross-site requests. It has three values:

ValueWhen cookie is sentUse for
Strict Only when navigating within the same site. Never on cross-site requests. High-security cookies (admin sessions, banking). May break links from external sites.
Lax Same-site requests + top-level GET navigations from other sites (a user clicking a link). Most session cookies. Good balance of security and usability. This is the browser default if SameSite is not set.
None` All requests including cross-site. Must be paired with Secure. Third-party cookies, embeds, payment widgets that must work inside iframes.

Without SameSite, the browser sends your session cookie on every request to your site — including those triggered silently by a malicious third-party page. This enables Cross-Site Request Forgery (CSRF): an attacker tricks your browser into making a request to your bank or webmail while you are logged in, performing an action on your behalf.

What the full header looks like

Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=86400

Nginx

proxy_cookie_flags ~ secure httponly samesite=lax;

Apache

Header edit Set-Cookie ^(.*)$ "$1; Secure; HttpOnly; SameSite=Lax"

Express (Node.js)

res.cookie('session', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'lax',
  maxAge: 86400000
});

PHP

session_set_cookie_params([
    'secure'   => true,
    'httponly' => true,
    'samesite' => 'Lax',
]);

Django (Python)

# settings.py
SESSION_COOKIE_SECURE   = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = 'Lax'
CSRF_COOKIE_SECURE      = True

What about the __Host- and __Secure- prefixes?

Cookie name prefixes are an additional protection layer:

  • __Secure-session — the browser will only accept and send this cookie if it was set with the Secure flag and from an HTTPS origin.
  • __Host-session — additionally requires the cookie to have no Domain attribute and Path=/. This locks it to the exact host, preventing subdomain attacks.

Rename your session cookie to __Host-session for the strongest available session-cookie protection in modern browsers.
