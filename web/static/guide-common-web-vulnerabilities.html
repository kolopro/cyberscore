Common website security vulnerabilities and how to fix them

The issues CyberScore finds most often — what each one is, why it matters, and the exact steps to fix it.

In short: Most websites fail on the same handful of issues: no HTTPS redirect, missing security headers, exposed server banners and no email authentication. All are fixable in an afternoon with server config changes — no code changes required.

1. HTTP not redirecting to HTTPS

Medium

What it is: Your site is accessible over both http:// and https://, but plain HTTP requests are not automatically redirected to the secure version. Users who type your domain without https:// (which is most users) may land on the unencrypted version.

Why it matters: Any data submitted on an HTTP page — including login forms, search queries and contact details — travels in cleartext and can be read or modified by anyone between the user and your server.

Fix (Nginx):

server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

Fix (Caddy): Caddy does this automatically when you specify your domain — no configuration needed.

2. Missing HSTS header

Medium

What it is: Strict-Transport-Security (HSTS) tells browsers to always use HTTPS for your domain — even before they get a redirect. Without it, a user's very first HTTP request (before the redirect) is unprotected and can be intercepted.

Fix: Add this header to HTTPS responses:

Strict-Transport-Security: max-age=63072000; includeSubDomains; preload

The preload directive lets you submit your domain to the browser's built-in HSTS preload list, so the first visit is also protected. Submit at hstspreload.org after the header is live.

3. No Content-Security-Policy

Medium

What it is: CSP tells the browser which scripts, styles, images and iframes are allowed on your page. Without it, any injected JavaScript — from an XSS vulnerability, a compromised third-party script or a browser extension — can read your users' data.

Starting point for a simple site:

Content-Security-Policy: default-src 'self'; img-src 'self' data:; script-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'
CSP is the most complex security header to get right. Start with Content-Security-Policy-Report-Only to see what it would block before enforcing it, so you don't break anything on your site.

4. Missing X-Frame-Options

Medium

What it is: Without this header, your site can be loaded inside an invisible iframe on a malicious page. This enables clickjacking: the user thinks they are clicking on something on the malicious page, but they are really clicking on your site behind it — submitting a form, making a purchase or changing account settings.

Fix:

X-Frame-Options: DENY

Or, if you need to allow framing from your own origin: X-Frame-Options: SAMEORIGIN. The modern equivalent is Content-Security-Policy: frame-ancestors 'none', which is more flexible.

5. Server version disclosed in headers

Low

What it is: The Server and X-Powered-By response headers often reveal your web server software and version (e.g. nginx/1.18.0, PHP/8.1.2). An attacker can use this to look up known vulnerabilities for that exact version.

Fix (Nginx):

server_tokens off;

Fix (Apache):

ServerTokens Prod
ServerSignature Off

Fix (PHP/X-Powered-By):

; in php.ini:
expose_php = Off

6. DMARC policy set to p=none

Medium

What it is: DMARC tells receiving mail servers what to do with emails that fail SPF and DKIM checks. A policy of p=none means "do nothing — just monitor." Your domain can still be used to send phishing emails that reach inboxes.

Fix: Gradually move to p=quarantine (send to spam) and then p=reject (block entirely).

_dmarc.example.com. TXT "v=DMARC1; p=reject; rua=mailto:dmarc@example.com; pct=100"

Start with p=none and a rua reporting address for a few weeks to see legitimate mail flows, then move to p=quarantine at pct=10, gradually increasing to pct=100 before switching to p=reject.

7. No SPF record

High

What it is: An SPF record tells receiving servers which IP addresses are allowed to send email for your domain. Without one, anyone can send email "from" your domain and many mail servers will deliver it.

example.com. TXT "v=spf1 include:_spf.google.com ~all"

Replace include:_spf.google.com with your actual mail provider's SPF include hostname. Use -all (hard fail) rather than ~all (soft fail) once you are confident you have listed all sending sources.

8. TLS 1.0 or 1.1 still enabled

Medium

What it is: TLS 1.0 (1999) and 1.1 (2006) are deprecated protocols with known weaknesses. Major browsers dropped them in 2020. Leaving them enabled extends your attack surface for no practical benefit.

Fix (Nginx):

ssl_protocols TLSv1.2 TLSv1.3;

Fix (Apache):

SSLProtocol all -SSLv3 -TLSv1 -TLSv1.1
